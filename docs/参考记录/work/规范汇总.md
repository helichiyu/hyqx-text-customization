### 2.2 命名规则

- **detection 值** = 主表工具英文名（如 `PTt_extract_pdf_body`），全局唯一，算子间不得复用
- **代码目录名** = detection 值（如 `PTt_extract_pdf_body/`），保持一比一可追溯。
  此约定优先于旧目录规范的 `{SS}_{CATEGORY}_{MODALITY}_{SEQ3}` 模板（依据 1.3 决策"命名以工具表格为准"）
- 示例算子旧命名（`t_file_exact_hash_dedup` / `TX_09_file_hash_dedup`）**不再沿用**；#12 开发时按
  `PTt_exact_hash_dedup` 重建标识，逻辑可复用示例代码

### 2.3 服务形态

默认**一算子一服务一镜像**（参照示例算子的自包含结构）。若联调期发现镜像数量带来的部署压力，
允许将依赖完全相同的纯规则算子合并为一个服务（`map.json` 支持多算子映射，按 detection 路由），
该调整不影响后端（后端只感知 URL + detection）。

## 3. 接口契约（传输层）

### 3.1 调用方式

```
POST /predict?detection=PTt_xxx
Content-Type: multipart/form-data
```

| 部分 | 说明 |
| --- | --- |
| query 参数 `detection` | 算子标识，固定值，见 2.1 表 |
| form 字段 `file` | **必填**。待处理文件。文本类算子通常为 JSON 文件：`{"text": "文本内容"}`；jsonl 文件每行一条记录，data[] 逐条返回 |
| form 字段 `param_xxx` | 选填。算子行为参数，见第 5 章 |
| form 文件字段 `fingerprint_library` / `lexicon` / `dictionary` / `topic_table` | 选填。状态库/资源库文件，见第 7、8 章 |

### 3.2 健康检查

```
GET /health   →   {"status": "healthy", "service": "PTt_xxx"}
```

容器启动完成后必须立即可用（供 K8s 探针与联调环境验证）。

### 3.3 HTTP 状态码使用规则

**业务成败一律放响应体（HTTP 200 + code 字段），HTTP 状态码只表达传输/协议层问题：**

| HTTP | 含义 |
| --- | --- |
| 200 | 调用受理，业务结果看 body 的 code/data |
| 400 | 协议错误：缺 file、param 值非法、multipart 格式错误 |
| 401 / 403 | 认证失败：缺少令牌 / 令牌校验不符（见 3.4） |
| 413 | 超过大小上限（见 6.2），快速失败 |
| 404 | 路径或 detection 不存在 |
| 500 | 服务内部异常（未捕获的崩溃） |
| 503 | 模型加载中/未就绪 |

后端只需实现一条处理链：HTTP 200 → 解析 body → 按 code 分流 → 遍历 data[] → 按 tags/action 做去向路由。

### 3.4 认证拦截（平台安全要求）

供给平台容器对外统一启用令牌拦截（依据《算子部署方案会议纪要·五、平台认证拦截解决方案》；
实现见 `common/auth_guard.py`，由 `common/server.py` 两种服务形态统一安装，**算子代码不感知**）：

| 项 | 约定 |
| --- | --- |
| 请求头 | `X-Token: <令牌>`（兼容 `token` 头） |
| 白名单 | `GET /health` 放行（K8s 探针 / Docker HEALTHCHECK 不带令牌） |
| 失败返回 | 缺令牌 `401 {"code":1,"msg":"AUTH_MISSING: ..."}`；令牌不符 `403 {"code":1,"msg":"AUTH_INVALID: ..."}` |
| 服务端存储 | 环境变量只存令牌 **SHA-256 摘要**（`AUTH_TOKEN_SHA256`，多调用方各持令牌时用空格/逗号分隔多个摘要）；联调可用明文变量 `AUTH_TOKEN`，摘要变量优先。摘要用 `secrets.compare_digest` 比对（防时序侧信道）；不采用 MD5（已不安全） |
| 文档端点 | 认证启用时自动关闭 `/docs` `/redoc` `/openapi.json`（避免被扫描出接口文档暴露） |
| 传输加密 | 令牌链路加密由网关/ingress TLS 承担（容器内为 HTTP）；容器内只落摘要，不落明文 |
| K8S 注入 | `kubectl create secret generic op-auth --from-literal=token=<令牌>`，环境变量 `AUTH_TOKEN` 经 `secretKeyRef` 引用（或直接注入摘要变量） |

## 4. 响应体外壳统一格式（核心约定）

### 4.1 外壳结构

所有算子、所有接口，响应体统一为：

```json
{
  "code": 0,
  "msg": "success",
  "data": [
    {
      "fieldName": "doc_001.json",
      "tags": ["重复文件"],
      "action": "remove",
      "...业务字段": "见 4.4 映射表"
    }
  ]
}
```

### 4.2 字段语义

| 字段 | 类型 | 必填 | 语义 |
| --- | --- | --- | --- |
| `code` | int | 是 | **技术层**执行结果：`0`=成功，`1`=失败。只回答"这次调用技术上成没成功"，与业务过滤判定无关 |
| `msg` | string | 是 | 人可读信息。成功为 `"success"`；失败给明确原因（如 `"PDF解析异常: 文档已加密"`），禁止空串 |
| `data` | array | 是 | **业务结果列表，统一为数组**（单文档时为长度 1 的数组）。jsonl 输入时每个元素对应一行记录，顺序与输入一致 |
| `data[].fieldName` | string | 是 | 记录标识，与输入记录对应用（文件名或 jsonl 记录 id）。批内多记录时后端靠它回溯原文档 |
| `data[].tags` | list | 是 | 业务标签数组，字符串**使用主表"拦截处理"列的标签原文**（见 4.3），供系统做去向路由与前端展示；无标签时为 `[]` |
| `data[].action` | string | 是 | 算子按**默认阈值**给出的建议动作：`keep`=保留 / `remove`=删除 / `review`=人工复核。最终决策权在系统侧配置阈值（见 5.4），算子不替系统做最终决定 |
| `data[].status` | int | 是 | **主表 U 列兼容字段**：`1`=放行/处理成功（action=keep），`0`=过滤/需复核（action=remove/review）。由 action 派生，与 action 同时返回；后端旧路由可直接读它，新路由仍以 action 为准 |

### 4.3 action/tags 与主表"拦截处理"列的对应

主表拦截处理列的"标签 → 动作 → 去向"由**系统执行**，算子负责提供依据：

| 主表拦截处理 | 算子返回 |
| --- | --- |
| 隔离 → 低质原始隔离区 | `tags: ["原始文件-损坏"]` 等 + `action: "remove"` |
| 拦截过滤 → 低质数据隔离库 | `tags: ["低质量数据-敏感"]` + `action: "remove"` |
| 脱敏替换后放行（不隔离） | `tags: ["命中个人信息"]` + `action: "keep"`（text 已是脱敏后文本） |
| 打标：疑似重复（人工确认） | `tags: ["疑似重复"]` + `action: "review"` |
| 打标统计，不进行过滤 | `tags: [主题/统计标签]` + `action: "keep"` |
| 指标达标与否由系统判 | 算子只返回指标字段（length/errorRate/rate…），`action` 给默认阈值下的建议 |

### 4.4 各算子业务字段映射总表

规范不复用旧规范的裸字段，业务字段放入 `data[]` 元素内。**字段名沿用旧规范已定义的命名**（text、hashValue、length、errorRate、rate、texts），保持文档间连续性：

| 算子 | data[] 业务字段 | 说明 |
| --- | --- | --- |
| #2 异常文件过滤 | `reason` | 可读原因（空文件/纯空白/编码异常/无法解析）；tags 用主表标签 `原始文件-损坏`、`原始文件-空`、`原始文件-编码异常`、`原始文件-无法解析` |
| #3~#8 六种正文提取 | `text` | 提取出的正文；失败时 `code=0`、`action="remove"`、tags=`原始文件-无法解析` |

### 4.5 错误处理

**批内单条失败不中断整批**：某条记录处理异常时，该条在 data[] 中返回
`{"fieldName": ..., "tags": ["处理失败"], "action": "review", "error": "原因"}`，
其余记录正常返回，整体 `code=0`。只有整次调用无法进行（文件缺失、参数非法、超限、模型未就绪）才 `code=1` 或走 4xx/5xx。

**错误分类枚举**（`data[].error` 或 `msg` 中引用，各算子 map.json 同步登记）：

| errorCode | 场景 |
| --- | --- |
| `FILE_EMPTY` | 空文件 |
| `FILE_CORRUPT` | 文件损坏/非声明格式 |

## 5. 算子行为参数传递约定

### 5.1 传递方式与命名

算子行为参数以 **multipart form 字段**随 `file` 一起提交（不使用 query 传参，避免 URL 编码歧义），命名规则：

```
param_ + 主表"工具配置项参数设计"列中的参数名（中文原名）
```

示例：`param_OCR识别=启用`、`param_滑动步长=128`、`param_保留词性=名词；动词；形容词`。

好处：前端配置项 ↔ 主表 ↔ 算子参数三方名称一比一对应，联调零翻译成本。

### 5.2 类型与取值规则

| 类型 | 规则 | 示例 |
| --- | --- | --- |
| 枚举 | 用主表枚举**中文原值**，不翻译成英文 | `param_分块策略=章节` |

## 6. 响应体大小上限约定

### 6.1 调用粒度

**一次调用 = 一个上传文件。** 文件可以是单文档，也可以是 jsonl 多文档（data[] 逐条返回）。
大语料由**系统侧拆片**后逐文件调用，算子不做分批调度。

### 6.2 上限与超限行为

| 项 | 初始约定 | 说明 |
| --- | --- | --- |
| 单次输入文件 | ≤ 10 MB | 超限返回 HTTP 413 + `{"code":1,"msg":"SIZE_EXCEEDED: 输入超过10MB"}` |
| 单次响应体 | ≤ 50 MB | 算子在序列化前预估（如 tokens 数组长度），预估超限直接 413 快速失败，不传一半超时 |
| 单批 jsonl 记录数 | 建议 ≤ 500 条 | 大输出算子（#26/#27/#37）由系统按此切片调用 |

数字为初始约定，**联调前与运维核对网关（nginx/ingress）的 `client_max_body_size`、响应缓冲与超时配置**后固化；如网关限制更严，以网关为准下调并同步本表。

### 6.3 大输出算子的专门控制

#26 MLM / #27 NSP / #37 Token 序列输出对输入有 3~5 倍放大（token id 数组 ×3 组字段），额外约定：

1. 优先返回**可读文本形式**样本（maskedText、sentenceA/B），token id 数组仅 `param_返回Token数组=启用` 时返回（默认关闭，交付训练时由 #37 打开）；
2. #37 单批 ≤ 500 条样本，超出由系统拆片；
3. 截断遵循"超长按分片结果截断，不静默丢弃"原则（与旧规范 4.33 一致），截断发生时在 `data[].tags` 加 `"已截断"`。

## 7. 去重指纹库回传约定

### 7.1 状态归属原则

去重是跨文件有状态计算，而算子必须无状态（多副本负载均衡、可随时重启、任务间隔离）。
**状态归系统保管，算子是纯函数**：

```
请求：本批文件 + fingerprint_library（可选，系统保管并回传的指纹库）
响应：判重结果 + newFingerprints（本批新增指纹，系统合并入库供下次调用带回）
```

算子**禁止**在请求间保留任何索引状态（示例算子的本地 `save_index()`/`dataset/hash_index` 机制废弃不用，
仅可用于本地测试）。

### 7.2 字段定义

**请求**（multipart 文件字段）：

```json
// fingerprint_library 文件内容
{
  "fingerprintType": "md5",          // md5 | simhash（#24 预留）
  "values": ["a1b2c3...", "..."]     // 已入库指纹值列表
}
```

**响应**（在统一外壳内追加两个顶层字段，与 code/msg/data 平级）：

```json
{
  "code": 0,
  "msg": "success",
  "data": [ { "fieldName": "doc_001", "hashValue": "a1b2c3...", "duplicateOf": [], "keepFileId": "doc_001", "tags": ["新文件"], "action": "keep" } ],
  "newFingerprints": ["a1b2c3..."],   // 本批新增（未与库重复、且批内首次出现）的指纹，系统负责合并
  "fingerprintType": "md5"
}
```

### 7.3 批内语义

同一批 jsonl 内部：相同指纹的记录，**首个** `action=keep`、tags=`新文件`；
后续相同者 `action=remove`、tags=`重复文件`、`duplicateOf=[首个记录的 fieldName]`。

### 7.4 对 #24（SimHash，暂缓）的扩展预留

指纹库约定按可扩展设计：`fingerprintType: "simhash"` 时 `values` 为 64 位 SimHash 指纹，
配合 `param_海明距离阈值`（默认对应 80% 块匹配率）判相似，命中输出 `similarity` 与
`tags:["疑似重复"]、action:"review"`（人工确认，不自动删除）。#24 开发时只需在本约定内
补充字段，不新开契约。

## 11. 性能与容量约定（大规模数据）

### 11.1 扩展模型

算子无状态 + 单次调用有界（第 6 章）+ 平台拆片调度。数据总量压力由**水平扩容**消化：
副本数 × 单副本吞吐 = 总吞吐，线性扩展。算子侧不需要为大语料做任何特殊改造。

### 11.2 服务性能基线（每个算子必须遵守）

| 项 | 要求 |
| --- | --- |
| 进程模型 | gunicorn/uvicorn 多 worker，worker 数 = CPU 核数；禁止单 worker 裸跑 |
| 模型加载 | 模块级单例 + 启动预热，禁止每请求加载 |
| JSON 序列化 | 使用 orjson（或 ujson），大 jsonl 解析必须流式逐行 |
| /health | 无重计算，仅返回状态 |
| 幂等 | 纯函数语义：同输入同输出，平台可安全重试 |

### 11.3 吞吐画像（交付物）

每个算子 README 必须实测报告，联调前汇总《算子容量规划表》交平台：

```
单副本吞吐：xx docs/s（注明文档平均长度）
单次调用耗时：p50 / p95
资源峰值：CPU xx 核 / 内存 xx MB / 是否需 GPU
模型加载时长：xx s（影响扩容冷启动）
```

### 11.4 重算力算子的专门约定

- **#5 PDF 提取（OCR）**：选型时出 CPU / GPU 两档资源画像；OCR 单页耗时与默认开关状态须与平台限流策略对齐
- **#37 Token 序列**：使用 fast tokenizer（tokenizers 库），禁用纯 Python 慢速分词

### 11.5 去重指纹库的规模化演进（对第 7 章的分级修正）

| 语料规模 | 方案 |
| --- | --- |
| < 10 万篇 | 第 7 章全量回传约定，不变 |
| ≥ 10 万篇 | 指纹库超出输入上限。**算子退化为纯哈希计算**：只返回 `hashValue` + 批内去重结果；全局判重由**系统侧数据库唯一索引**完成（系统本就执行去向路由，顺带完成判重）。`fingerprint_library` 字段保留但可不传 |
| #24 近似去重（百万级） | MinHash/LSH 索引必须分片或分布式实现（任务书亦按 Spark map-reduce 设计），暂缓期内与平台共同定方案，不在单算子 HTTP 调用内解决 |

### 11.6 压力归属划分（与平台的边界）
