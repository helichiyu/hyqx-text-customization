# 数据库开发通用规范

> 适用对象：在 `192.168.1.102` 这套开发/测试服务器上新建项目、需要新建数据库并开发前后端的团队。
> 制定依据：`iflytek-obu-pre-training` 生产库（`iflytek_obu_pre_training_db`，65 张业务表、44 个迁移脚本）已经验证落地的口径。
> 目的：新项目与现有系统共用同一台服务器、同一套中间件时，不串库、不串会话、不撞约束、运维可统一管理。

---

## 一、总则

1. **同实例，不同库，绝不共表。** 新项目在现有 MySQL 实例上建自己的库；禁止往已有项目的库里加表、改表。
2. **库名必须以 `db` 结尾。**
3. **连接信息（地址、账号、密码、Redis、CAS、UAP、S3）统一向运维申请**，不要自行猜测或复用其他项目的账号。
4. 所有结构变更必须留下脚本，不允许只在图形客户端里手改。

---

## 二、实例与建库

| 项 | 约定 |
|---|---|
| MySQL 实例 | `192.168.1.102:13306`（102 服务器 docker 容器 `mysql`） |
| 连接账号 | 向运维申请（现有为 `ai`），密码不得以明文入库/入 git |
| 库命名 | `<业务英文名>_db`，例：`iflytek_obu_pre_training_db` |
| 字符集 | `utf8mb4` |
| 排序规则 | `utf8mb4_unicode_ci` |

建库语句：

```sql
CREATE DATABASE `xxx_db`
  DEFAULT CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;
```

> 建库前先确认库名未被占用：
> `SHOW DATABASES LIKE 'xxx_db';`

## 三、表设计规范

### 3.1 标准建表模板（新表直接照抄）

```sql
DROP TABLE IF EXISTS `tb_xxx_yyy`;
CREATE TABLE `tb_xxx_yyy` (
  `id`          bigint       NOT NULL COMMENT 'id',
  `xxx_no`      varchar(64)  NOT NULL COMMENT '业务编号（唯一）',
  `name`        varchar(200) NOT NULL COMMENT '名称',
  `status`      varchar(32)  NOT NULL DEFAULT 'INIT' COMMENT '状态枚举：INIT/PROCESSING/DONE/FAILED',
  `remark`      varchar(500) DEFAULT NULL COMMENT '备注',
  `creator`     bigint       DEFAULT NULL COMMENT '创建者',
  `create_date` datetime     DEFAULT NULL COMMENT '创建时间',
  `updater`     bigint       DEFAULT NULL COMMENT '更新者',
  `update_date` datetime     DEFAULT NULL COMMENT '更新时间',
  `del_flag`    tinyint      NOT NULL DEFAULT 0 COMMENT '删除标记 0未删除 1已删除',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_xxx_no` (`xxx_no`),
  KEY `idx_status` (`status`),
  KEY `idx_create_date` (`create_date`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='中文表注释';
```

### 3.2 强制规则

| 规则 | 要求 |
|---|---|
| 表前缀 | 一律 `tb_`；模块内再分组，如 `tb_prod_*`、`tb_corpus_*`、`tb_coll_*` |
| 主键 | `id bigint NOT NULL`，使用**雪花 ID**（MyBatis-Plus `ASSIGN_ID`），**不用自增** |
| 审计字段 | 每张业务表必须包含 `creator`、`create_date`、`updater`、`update_date`、`del_flag` 五列，命名与类型不得改 |
| 逻辑删除 | 查询恒带 `del_flag = 0`；需要留痕的删除只置 `del_flag = 1`，物理删除仅用于确认无留痕需求的数据 |
| 表/列注释 | **每张表、每一列都必须有中文 COMMENT**，不允许空注释 |
| 外键 | **不使用 FOREIGN KEY**，关联关系由应用层维护 |
| 时间字段 | 一律 `datetime`，**不使用 `timestamp`** |
| JSON 数据 | **不使用 MySQL `json` 类型**，用 `text` / `mediumtext` 存 JSON 字符串 |
| 状态字段 | 用 `varchar(32)` 存大写英文枚举；只有纯 0/1 开关才用 `tinyint` |
| 命名风格 | 表名、列名全小写 + 下划线；布尔语义用 `is_xxx` 或 `xxx_flag` |
| 字符集 | 每张表显式声明 `DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci` |
| 引擎 | `InnoDB` |

### 3.3 字段类型选择

| 场景 | 类型 |
|---|---|
| 主键 / 外键关联 ID / 人数类 ID | `bigint` |
| 状态、类型、枚举 | `varchar(32)` |
| 编号、编码 | `varchar(64)` |
| 名称 | `varchar(200)` |
| 备注、原因 | `varchar(500)` |
| URL / 文件路径 | `varchar(500)` |
| 普通长文本、JSON | `text` |
| 大文本、报告、明细 JSON | `mediumtext` |
| 评分、比例、金额 | `decimal` |
| 计数、进度 | `int` / `bigint` |
| 开关、删除标记 | `tinyint` |
| 时间 | `datetime` |

## 四、索引与约束

1. 唯一键命名 `uk_<含义>`，普通索引命名 `idx_<含义>`。
2. 唯一业务编号（如 `task_no`、`biz_no`）必须建唯一索引，靠数据库兜底并发重复。
3. 高频查询条件（`task_id`、`status`、`create_date`）必须建索引，禁止无索引的全表扫描查询上线。
4. 组合索引遵循最左前缀，列顺序按"等值在前、范围在后"排列。
5. 不使用外键、不使用触发器、不使用存储过程做业务逻辑（迁移脚本里临时用存储过程做幂等判断除外，用完即删）。

## 五、数据库迁移脚本规范

项目**不使用 Flyway / Liquibase**，采用手写 SQL + 按序人工执行的方式。

### 5.1 目录与命名

```
docs/db/
├── migrations/                      # 增量迁移，唯一权威
│   ├── V20261026_04__biz_no_task_dataset.sql
│   └── V20261027_01__base_gaps.sql
└── xxx-schema.sql                   # 全量基线（新环境初始化用）
```

- 文件名格式：`VyyyyMMdd_NN__<英文短描述>.sql`
- `NN` 为当日序号，从 `01` 递增，两位补齐
- 一个脚本只做一件事，标题写清楚

### 5.2 幂等要求（强制）

迁移脚本必须可重复执行且不报错。新增列/索引前先查 `information_schema`：

```sql
DELIMITER $$

DROP PROCEDURE IF EXISTS ensure_column $$
CREATE PROCEDURE ensure_column(IN p_table VARCHAR(64), IN p_column VARCHAR(64), IN p_ddl TEXT)
BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM information_schema.COLUMNS
    WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = p_table AND COLUMN_NAME = p_column
  ) THEN
    SET @ddl = CONCAT('ALTER TABLE `', p_table, '` ADD COLUMN `', p_column, '` ', p_ddl);
    PREPARE stmt FROM @ddl;
    EXECUTE stmt;
    DEALLOCATE PREPARE stmt;
  END IF;
END $$

DELIMITER ;

CALL ensure_column('tb_xxx_yyy', 'new_col', 'VARCHAR(64) DEFAULT NULL COMMENT ''新列''');

DROP PROCEDURE IF EXISTS ensure_column;
```

### 5.3 执行要求

1. 新增迁移脚本时，**同步更新**对应的 `xxx-schema.sql` 全量基线。
2. 脚本头部写清：用途、影响的表、是否幂等、回滚方式。
3. 应用启动时建议加 schema 守卫：校验关键表/列是否存在，缺列直接启动失败，避免运行期 schema 漂移。
4. 迁移脚本按编号顺序执行；已执行的脚本不再修改，修正用新编号追加。

## 六、连接与 ORM 配置

### 6.1 JDBC 连接串（统一格式）

```
jdbc:mysql://192.168.1.102:13306/<db>?autoReconnect=true&useUnicode=true
&characterEncoding=UTF-8&useSSL=false&allowMultiQueries=true
&allowPublicKeyRetrieval=true&serverTimezone=Asia/Shanghai
```

参数说明：

| 参数 | 作用 | 是否必须 |
|---|---|---|
| `useUnicode=true&characterEncoding=UTF-8` | 中文不乱码 | 必须 |
| `serverTimezone=Asia/Shanghai` | 时间不偏移 8 小时 | 必须 |
| `allowMultiQueries=true` | 支持多语句 SQL | 建议 |
| `allowPublicKeyRetrieval=true` | MySQL 8 认证 | 建议 |
| `useSSL=false` | 内网免证书 | 按环境 |

### 6.2 连接池与 ORM

- 连接池：**Druid**
- ORM：**MyBatis-Plus**
  - `map-underscore-to-camel-case: true`（下划线列名自动映射驼峰属性）
  - `call-setters-on-nulls: true`
  - `id-type: ASSIGN_ID`（雪花 ID）
  - `log-impl: org.apache.ibatis.logging.slf4j.Slf4jImpl`
    **不要用 `StdOutImpl`**：高并发下会把执行线程全部阻塞在 stdout 上。

### 6.3 敏感配置

- 数据库、Redis、S3 的密码**一律加密后入库/入配置文件**（现网用 jasypt `ENC(...)`）。
- 主密钥通过环境变量注入（`JASYPT_ENCRYPTOR_PASSWORD`），不写进 git。
- 禁止明文密码出现在任何提交、日志、文档中。

---

## 七、Redis 使用隔离

- 现有系统占用 `db3`（且与基座共用登录会话，命名空间不可改）。
- **新项目必须单独申请一个 Redis db 号**，不得复用其他项目的 db。
- 必须支持 Sentinel 模式，节点、密码向运维申请。
- 会话 key 前缀建议加项目名，避免人工排查时混淆。

---

## 八、基座表与菜单权限

- `sys_menu`、`sys_role`、`sys_role_menu`、`sys_user`、`sys_params` 为基座自带表，**不要自行改动结构**。
- 新环境初始化时向运维/基座负责人获取基座 DDL，不要自己造。
- 菜单 ID 使用固定段位，新项目必须**另起一段**，避免与现有菜单主键冲突（现有超管角色 ID 为 `1067246875800000001`，业务菜单从 `1067246875800010001` 起）。
- 权限串格式固定：`模块:实体:动作`，如 `prod:task:page`、`prod:task:save`、`prod:task:delete`。

---

## 九、业务编号规范

需要对外展示的业务编号，统一格式：

```
<前缀> + <yyMMdd> + <6位安全随机码>
例：TASK261026A1B2C3
```

- 前缀为 2–4 位大写字母，**先在编号前缀字典中登记后才能使用**，避免与其他项目撞号。
- 业务编号列必须建唯一索引，生成时依赖唯一索引做碰撞重试。
- 存量数据补编号由启动回填任务完成，新增数据写入时即时生成。

## 十、新库初始化顺序

1. 申请：库名、账号权限、Redis db 号、S3 桶名。
2. 建库（第二节语句）。
3. 导入基座表（`sys_*`）。
4. 执行业务全量基线 `xxx-schema.sql`。
5. 按编号顺序执行 `migrations/` 下脚本。
6. 导入菜单、角色、字典等种子数据。
7. 启动应用，确认 schema 守卫通过、能正常读写。

## 十一、上线前检查清单

- [ ] 库名以 `db` 结尾，字符集 `utf8mb4` / `utf8mb4_unicode_ci`
- [ ] 所有表 `tb_` 前缀，主键 `bigint` 雪花 ID
- [ ] 每张表都有 `creator/create_date/updater/update_date/del_flag` 五列
- [ ] 表、列全部有中文注释
- [ ] 无外键、无 `timestamp` 列、无 MySQL `json` 类型
- [ ] 唯一业务编号已建唯一索引
- [ ] 所有查询条件字段有索引，`EXPLAIN` 无全表扫描
- [ ] 迁移脚本幂等，已同步全量基线
- [ ] JDBC 串含 `characterEncoding=UTF-8` 与 `serverTimezone=Asia/Shanghai`
- [ ] 密码全部加密，无明文提交
- [ ] Redis 使用独立 db 号
- [ ] 菜单权限串符合 `模块:实体:动作` 格式，菜单 ID 使用独立段位

## 十二、常见坑

| 现象 | 原因 | 处理 |
|---|---|---|
| 中文乱码 | 表/库字符集不是 `utf8mb4`，或导入 SQL 未指定编码 | 建库建表统一 `utf8mb4`；导中文 SQL 加 `--default-character-set=utf8mb4` |
| 时间差 8 小时 | JDBC 缺 `serverTimezone` 或列用了 `timestamp` | 连接串补参数，统一用 `datetime` |
| 并发插入重复编号 | 业务编号未建唯一索引，仅靠应用层判重 | 建 `uk_` 唯一索引，应用层做碰撞重试 |
| 启动后读写报列不存在 | 迁移脚本未执行，schema 漂移 | 加启动期 schema 守卫，缺列直接失败 |
| 会话串号 / 登录状态互相覆盖 | 与他人共用 Redis db 和默认命名空间 | 独立 db 号 + 项目专属 key 前缀 |
| 改了配置不回滚导致重复执行报错 | 迁移脚本不幂等 | 全部先查 `information_schema` 再建 |
| 生产执行线程卡死 | MyBatis 日志用了 `StdOutImpl` | 改用 `Slf4jImpl` |

---

## 十三、需要运维配合的事项

1. MySQL 实例地址、账号、密码、新库权限授予。
2. Redis Sentinel 节点、密码、**新项目专属 db 号**。
3. S3/MinIO 桶名（**每项目独立桶**，不要共用别人的桶）。
4. 基座 `sys_*` 表 DDL 与菜单初始化脚本。
5. 业务编号前缀登记。

以上事项联系运维屈桐。
