## 32.1 ID 生成规范（全站统一，禁止各组自创）

**背景与文档价值**

编号是平台中任务、数据集、策略、算子、配置等业务对象的**唯一标识**，既用于用户查看、检索、复制与口头沟通，也用于系统内部关联和对外接口对接，是用户感知系统"专业与否"的高频细节。

当前平台由多个研发组并行开发、大量页面与原型由 AI 生成，编号缺少统一规则：**有长有短、有纯数字、有随机拼接、有自增序列，格式五花八门**，既不美观、可识别性差，也带来实际隐患——自增 ID 会暴露业务总量、可被逐条遍历抓取，随意拼接的编号还可能包含敏感信息。

本规范用于统一全站编号的**结构、长度、前缀与生成方式**，目标是：

+ 让编号**易读、易检索、可复制、可沟通**，各业务线呈现一致、专业；
+ 让编号**无规律、不可枚举、不含敏感信息**，规避数据泄露与安全风险；
+ 为研发组和生成原型的 AI 提供唯一标准，**不再各做各的**。

适用范围：平台所有业务对象的编号生成、展示与对接；受众：产品、研发、测试，以及生成原型的 AI。

---

平台对象（任务、数据集、策略、算子、配置、模型…）的 ID 分**三层**，各有用途，不允许混用或自创格式。

**第一层：内部主键（系统内部，不对外）**

+ 算法：**雪花算法 Snowflake**，19 位长整型（如 `2074457061897732097`）。
+ 特点：全局唯一、趋势递增、分布式可用、按时间有序。
+ 用途：数据库主键、内部表关联。
+ **不直接暴露在对外 URL / 分享链接中**（避免业务量被推算、记录被遍历）。

**第二层：业务编号（用户可见、可搜索、可口头沟通）**

+ 格式：`业务前缀 + 日期 + 随机码`
+ 结构：`前缀(2–4 位大写字母)` + `yyMMdd(6 位)` + `6 位随机码`，总长 **14–16 位**。
+ 示例：`TASK261026A3F9KX`、`DS261026K7M2PQ`。
+ 随机码字符集：去掉易混淆的 `0/O、1/I/L`，只保留 31 个安全字符（数字 2–9 + 大写字母除 I/L/O），用**密码学安全随机（CSPRNG）**生成，不用普通 `rand()`。
+ 容量：单日单类型可承载万级（6 位随机空间约 8.8 亿，日产量超万的对象随机位加到 8 位）。

**第三层：语义化编码（程序对接，稳定不变）**

+ 用于程序调用、接口对接，需稳定、可读，如算子调用编号 `042t_education_discrimination`。
+ 规则：小写字母 + 数字 + 下划线，`模块前缀_英文语义`，一旦发布不可更改。

**ID 安全铁律**：

1. **对外禁止用自增 ID（1,2,3…）**——会暴露总量、可被逐条遍历抓取。
2. 对外 / 分享 ID 必须**无规律、不可预测、不可枚举**；对外 URL 用业务编号，**不用雪花 ID**。
3. ID 中**不含任何敏感信息**（手机号、身份证、姓名、邮箱、单位名）。
4. 随机数必须用**密码学安全随机**；长度、前缀、格式全站统一。
5. 业务编号一律 **monospace 等宽字体展示**，可一键复制；不在 ID 里加空格或特殊符号。

**ID 生命周期与边界规则**：

1. **ID 不复用**：记录删除 / 作废后，该编号永久不再分配给其他对象。
2. **碰撞重试**：写入时若唯一约束冲突（极小概率），自动重新生成，不报错给用户。
3. **历史数据兼容**：老系统已有 ID 不强制改造，通过映射表过渡，新数据一律走新规范。
4. **日期基准**：编号中日期统一按服务器时区（UTC+8）生成；业务编号统一大写，语义编码统一小写。
5. **多租户 / 环境**：租户隔离由系统层保证，不写入 ID；测试与生产环境 ID 不混用。
6. **长 ID 展示**：表格中 ID 列固定等宽字体，超长截断 + tooltip 显示完整值 + 复制按钮。
